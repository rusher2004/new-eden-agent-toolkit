# neat — New Eden Agent Toolkit

Go MCP server + Claude Code plugin + Claude Desktop extension for interacting with EVE Online via
CCP's ESI API and the EVE Ref Static Data Export (SDE). Design spec:
`docs/superpowers/specs/2026-07-23-foundation-design.md`.

## Architecture

Flat package structure at repo root. No `internal/`. One package per responsibility:

| Package | Responsibility |
|---|---|
| `cmd/` | `main.go` entrypoint only |
| `commands/` | `urfave/cli/v3` command tree (`version`, `setup`, `mcp`) |
| `config/` | Non-secret state in `~/.neat/config.json`: logged-in characters, plus named facility, haul and hub profiles for industry planning |
| `creds/` | OS keychain wrapper (`zalando/go-keyring`), service name `"neat"` |
| `sso/` | ESI OAuth2/PKCE login flow: state generation, a loopback browser session for the redirect (`session.go`: an HTTP server on `127.0.0.1:48211`, bound only while `add_character` runs, serving `/callback` plus a page listing the user's characters with "Add another character" and "I'm done" buttons, embedded from `sso/web/`), orchestration via `github.com/fnt-eve/goesi-openapi`, refresh-token persistence via `creds/`. The redirect URI `http://127.0.0.1:48211/callback` must match the ESI application's registered callback URL exactly, so the port is fixed. The session ends when the user clicks Done, closes the tab (a `pagehide` beacon, backed by a 30-second ping timeout), or a login gets no callback within 5 minutes; it accepts only its own `Host` header (DNS rebinding) and a per-session page token on every POST (CSRF), and each OAuth2 state is single-use. `scopes.go` defines the scope groups a login can request (`ScopeGroups`; `basic` always, the rest chosen per login, so no login asks for all 72 scopes at once) and `GrantedScopes`, which reads a character's granted scopes from its current access token's `scp` claim. All outbound requests to CCP (JWKS fetch, OAuth2 token exchange) carry `sso.UserAgent(version)`, per ESI's User-Agent best practices. Also caches a per-character auto-refreshing HTTP client (`AuthenticatedClient`/`RemoveCharacter`) for `esi/`'s use — refreshing relies entirely on `golang.org/x/oauth2`'s own token source (with rotated refresh tokens persisted back to `creds/` if CCP ever returns one), not hand-rolled expiry tracking. `AuthenticatedClient`, `RemoveCharacter`, and `add_character`'s token save share one mutex across their entire keychain operation, not just the cache map, so none can interleave. Re-adding an already-known character (e.g. after CCP revoked its refresh token) evicts that character's cached client along with saving the new token, so the fresh login takes effect immediately rather than after a process restart |

## Known gaps (tracked, not silently accepted)

- ~~CCP added a 37th ESI tag, "Military Campaigns" (6 endpoints), blocked on an upstream `goesi-openapi` release.~~ Resolved in the 2026-11-18 SDE/ESI audit: `goesi-openapi` v0.0.42 (generated against compatibility date 2026-08-18) ships bindings for it plus two more tags CCP added since, Cosmetics (3) and Paragon Hub (5), and all 14 endpoints are now implemented. See `docs/reference/esi-coverage-roadmap.md`.
- **EVE Ref's `esi-scrape` dataset has not been regenerated since 2025-11-26** (found in the 2026-11-18 audit: EVE Ref's own `esi-scrape/index.json` gives `eve-ref-esi-scrape-latest.tar.xz` a `last_modified` of 2025-11-26T15:42:24Z, the archive's `status.yaml` snapshot is of server build 3116156 started that morning, and `history/2025/` ends with that day's snapshot; Cloudflare's `Last-Modified` header looks current but is synthesized at the edge, differing between simultaneous requests). `sde/` still fetches it for race `AllianceID` and graphic `SofDNA`, which are rarely-changing enough that a year-stale copy is still correct for every existing race and nearly every graphic, but anything CCP added since is missing from it. EVE Ref's still-current `reference-data` export has no race or graphic files, so it can't replace `esi-scrape` for these two (it does replace it as type `Radius`'s source -- see Hard rules). Revisit if EVE Ref resumes publishing, or if a graphic's `SofDNA` going missing turns up in practice.
- ~~No CI configuration exists in this repo at all.~~ Resolved: `.github/workflows/test.yml` runs `go build`/`go vet`/`go test -race` on real `ubuntu-latest`, `macos-latest`, and `windows-latest` runners on every push/PR.
- ~~Cross-process TOCTOU in `sso.bindExclusive`'s stale-socket recovery path.~~ Gone with the Unix-socket handoff: a second `neat` process is now kept out by the exclusive TCP bind of the callback port, which the OS makes atomic, and a crashed process leaves no file behind to recover.
- ~~The browser tab never closes/navigates after a successful `add_character` login.~~ Resolved by moving the OAuth2 redirect from the `eveauth-neat://` custom scheme to a loopback HTTP server (`docs/superpowers/specs/2026-11-19-loopback-oauth-callback-design.md`): CCP's tab now lands on neat's own page.
- **The callback port is fixed (48211)**, because CCP's SSO matches the registered callback URL exactly and doesn't implement RFC 8252 §7.3's any-port loopback matching. If another program holds the port, `add_character` fails with an error naming it rather than falling back. Revisit if CCP ever accepts any-port loopback redirects.
- **Installs that ran neat 0.7.x or earlier keep their old `eveauth-neat://` registration**: `~/.neat/NeatURLHandler.app` registered with Launch Services on macOS, `HKCU\Software\Classes\eveauth-neat` on Windows, and `~/.local/share/applications/neat-url-handler.desktop` on Linux, plus the launcher copy at `~/.neat/bin/neat`. Nothing redirects to that scheme any more, so they sit inert; no code removes them, and a user can delete them by hand. Same trade-off as the orphaned bbolt file below.
- **`~/.neat/sde/sde.db` (the old bbolt cache file) is orphaned by the sqlite migration** and never
  cleaned up automatically -- no migration code deletes it, so it sits inert on disk for any
  install that previously ran the bbolt-backed `sde/`. A user can delete it by hand; see
  `docs/superpowers/specs/2026-08-04-sde-sqlite-migration-design.md`'s "Fetch & freshness" section.
- **`sde.Store`'s in-memory overlay (`PutX`'s cache-miss write-back) is invisible to every
  `*IDs`/list accessor** (`RegionIDs`, `TypeIDs`, `Factions`, ...) -- they query the sqlite dump
  only. A `GetX(id)` can succeed for an ID a `PutX` just wrote back from a live ESI fetch, while
  the matching `*IDs()`/list call never includes it, since the two paths look at different stores.
  Surfaces only for a genuinely new ID CCP added after the fuzzwork dump's last refresh -- rare,
  self-healing at the next refresh. Deliberately not fixed by merging overlay entries into every
  `*IDs`/list result: real complexity for an edge case that resolves itself. See `sde/store.go`'s
  `overlay` field doc comment.

## Hard rules

- **Prefer a cached, statically-refreshed source over a live per-request ESI call**: any tool needing a resource available from CCP's SDE or from EVE Ref's `esi-scrape` bulk export must read it from `sde/`, never call ESI for it directly. Performance and API-citizenship requirement, not a suggestion. `sde/` is backed by a single downloaded file — fuzzwork.co.uk's SQLite conversion of CCP's SDE, ETag-checked and re-downloaded once per process lifetime on change (sync-fatal on failure) — queried directly via SQL, no intermediate key-value store. Three fields with no source in that file come from narrow, in-memory-only fetches against EVE Ref (best-effort — a fetch or parse failure there logs a warning and skips that field's augmentation, never fails the rest of the sync): race `AllianceID` and graphic `SofDNA` from the `esi-scrape` dataset, and type `Radius` from the `reference-data` dataset. Type `Radius` moved there in the 2026-11-18 audit, when fuzzwork dropped `invTypes.radius`; until `sde/type.go` stopped selecting it, every `Type` lookup failed with "no such column: radius", which broke `get_universe_type` outright and silently blanked every `TypeName` enrichment. Type `PackagedVolume` was sourced from `reference-data` too, until CCP added it to the SDE itself (https://github.com/esi/esi-issues/issues/1499) and fuzzwork's dump picked it up as a plain `invTypes.packagedVolume` column — `sde/type.go`'s `Type` reads it straight off that column, same as `mass`/`volume`/etc. 24 of the Universe tag's 30 tools are `sde/`-backed via a read-through cache: try `sde/` first, fall back to a live ESI call on a cache miss, write the result back (into a process-lifetime in-memory overlay, not the downloaded file, which is treated as read-only) so the next lookup of that ID is fast. The other 6 (`list_universe_structures`/`get_universe_structure`, `list_universe_system_jumps`/`_kills`, `resolve_universe_ids`/`_names`) are permanently ESI-direct by design -- they resolve live, non-cacheable data (structures are player-owned and access-gated; jumps/kills are moment-in-time activity counters; the resolve tools take arbitrary caller-supplied names/IDs), not an SDE sourcing gap. Four fields have no source anywhere in the fuzzwork dump: `get_universe_graphic`'s `CollisionFile` (also absent from EVE Ref's `esi-scrape` mirror of ESI's own live responses -- unaffected by the sqlite migration), `get_universe_region`'s `Description` (`mapRegions` has no description column at all -- a genuine regression from the prior bbolt design, which sourced it from CCP's own jsonl), `get_universe_station`'s `Services` (`staOperationServices` has zero rows in the dump), and `list_universe_factions`'s `IsUnique` (`chrFactions` has no `uniqueName`-equivalent column). Each is populated on a cache miss (fresh off ESI) but not on a cache hit -- documented in `docs/superpowers/specs/2026-08-04-sde-sqlite-migration-design.md`'s field-drop findings. The `reference-data`/`esi-scrape` fetches are unconditional on every `sync()` call, not ETag-gated like the main dump -- their results are never persisted to disk, so there's nothing for a gate to compare against, trading bandwidth on every launch for correctness. The main dump itself remains ETag-gated as described above.
- **Industry bonuses come from the SDE, not code**: structure role bonuses, rig bonuses and each rig's own security multipliers, which products each rig or structure affects (`indModifierSources` + `indTargetFilter*`), refinery yield bonuses, implant bonuses and jump drive attributes are all read from the fuzzwork dump at use time. The only numbers kept in code are those with no SDE source, each a named constant in `industry/constants.go` citing where it comes from (SCC surcharge, Alpha tax, tax cap, NPC facility tax, reprocessing base and rig/security terms, invention base chances and decryptors, research level durations, the light-year constant). Facts ESI can't see (fitted rigs and services, owner taxes, hauling hull and routes, routing preferences) live in saved profiles in `~/.neat/config.json`, never as hard-coded assumptions.
- **Logins request scope groups, never every scope**: `add_character` asks CCP for the `basic` group plus the groups the user picked (`sso/scopes.go`), and a tool needing more fails with `esi.MissingScopeError` until the user re-authorizes. Requesting all scopes in one login pushed CCP's login-site cookies past its request-header limit after a couple of logins ("HTTP Error 400. The size of the request headers is too long"). Every scope an ESI endpoint needs must belong to exactly one group; `esi`'s and `sso`'s tests enforce it, so a `goesi-openapi` bump that adds an endpoint with a new scope fails CI until the scope is grouped.
- **No environment variables for config/credentials.** Config lives under `~/.neat/`; credentials
  live in the OS keychain only.
- **No client secret.** The ESI app is a PKCE-only public app — nothing secret ships in the binary.
- **ESI User-Agent compliance**: every outbound request to CCP's login/ESI endpoints must carry `sso.UserAgent(version)`. CCP's best-practices guidance treats non-compliant User-Agents as grounds for a temporary ban — see `sso/useragent.go`.
- **ESI error detail must not be discarded**: every `esi/` method that calls `.Execute()` on a generated API request must route its error and `*http.Response` through `describeError` (`esi/error.go`) before wrapping and returning it. `goesi-openapi`'s generated error type degrades to a bare HTTP status string on its own — its message formatter looks for `Title`/`Detail` fields via reflection, but ESI's actual error model uses `Error`/`Details` instead, so the real detail (invalid scope, expired token, etc.) and the `X-Esi-Error-Limit-Remain`/`-Reset` rate-limit headers are silently lost unless routed through this helper. Confirmed via direct reproduction against `goesi-openapi` v0.0.37 — see `esi/wallet.go` for the pattern every new `esi/` method should follow. When no ESI error detail can be extracted, notably when a 2xx response fails to decode into the generated model, `describeError` appends the raw response body (truncated to 512 bytes) instead, so the error shows what ESI actually sent rather than only what the model expected.

## Conventions

- Wrap errors with context: `fmt.Errorf("operation: %w", err)`. Never discard an error (`_ = err`).
- External test packages by default (`package foo_test`); use `*_internal_test.go` only when a
  test genuinely needs an unexported symbol.
- Table-driven where a table naturally fits (many input variations on one code path);
  independent, clearly-named tests otherwise — don't force behaviorally distinct scenarios into
  one table just to have a table. Standard library only, either way — no `testify` or other
  assertion libraries.
- `creds/` tests must call `keyring.MockInit()` before touching keychain functions — never let
  tests hit the real OS keychain.
- Never model a nested/tree-shaped ESI resource with a self-referential Go struct (a type whose
  field is `[]ThatSameType`). It passes `go build`/`go vet`/`gofmt` but panics at server startup
  ("cycle detected for type ...") in the MCP SDK's output-schema generator — only `go test ./...`
  actually calling `mcpsdk.AddTool` catches it. Instead, define one distinct, non-recursive type
  per real nesting level, matching the ESI schema's actual depth (see `mcp/killmails.go`'s
  `KillmailItem`/`KillmailInnerItem` split).

## Keeping docs & Claude resources in sync

`neat` is consumed by both humans and agents through several surfaces that must not drift from the
code. **When a change affects behavior, update the relevant surfaces in the same commit/PR** —
treat it as part of "done," not a follow-up:

- **Packages / architecture** → the package table and conventions in **this `CLAUDE.md`**, and
  `README.md`'s architecture section. Note significant departures from
  `docs/superpowers/specs/2026-07-23-foundation-design.md` in that spec's own status line rather
  than rewriting it — it's a historical record of what was decided, not a living doc.
- **CLI surface** (new command, flag, or exit-code contract) → `README.md`'s Build/Test/usage
  section and this file's package table.
- **Credentials** (new keychain key, service name, or verification flow) → `creds/`,
  `commands/setup.go`, and the Hard rules / Conventions sections here.
- **Hard rules** (SDE-vs-ESI routing, no client secret, no env vars for storage) → keep these
  listed here exactly as they're enforced in code; if a rule is relaxed or tightened, this file
  changes in the same commit as the code that changes it.
- **Plugin skills** (`claude_resources/neat/skills/*/SKILL.md`: `add-character`, `industry-build-plan`, `industry-profile-setup`, `haul-route-setup`) → when `add_character`'s or an industry, hauling or routing tool's inputs, outputs or behavior change, or a scope group changes, update the skill that drives it in the same commit. Skills hold discovery and decision steps only — never formulas or arithmetic.
- **Agent-facing surfaces that don't exist yet** — once built in a later plan, add them to this
  list: the Claude Desktop extension (`extension/manifest.json`), and any `reference/*.md`
  API-contract docs. Don't leave a plan's own doc updates (e.g. its plan file, or a spec status
  line) as a "follow-up" task.

Before opening a PR, sanity-check that `README.md` and this file still describe what the code
actually does.

## Build

`clientID` (the ESI OAuth2 client ID) is injected via `-ldflags` from the git-ignored `app_config.json` — `make build` wraps this for local development.

```bash
go build -ldflags "-X main.version=$(cat VERSION 2>/dev/null || echo dev) -X main.clientID=$(jq -r .clientId app_config.json)" -o neat ./cmd
```

## Versioning & Release

The top-level `VERSION` file is the single source of truth for the `neat` binary version, the
Claude Code plugin manifest version, and the release git tag. `tools/genversion` (wired via
`go:generate` in `cmd/main.go`) propagates it into `claude_resources/neat/.claude-plugin/plugin.json`
— run `go generate ./...` after bumping `VERSION` and commit the result.

`tools/versiongate` is a required PR check: any PR touching release-significant files (Go source,
`go.mod`/`go.sum`, `.goreleaser.yaml`, anything under `claude_resources/`) must bump `VERSION`. Docs,
tests, and CI config are exempt. There is no override — bump it.

Merging to `main` triggers `.github/workflows/release.yml`, which tags `v<VERSION>` (if that tag
doesn't already exist) and runs GoReleaser to build/publish `neat` for linux/darwin/windows.
