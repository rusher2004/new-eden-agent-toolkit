# neat — New Eden Agent Toolkit

Go MCP server + Claude Code plugin for interacting with EVE Online via Fenris Creations' (FC's) ESI API and a local copy of FC's Static Data Export (SDE). It also works in the Claude desktop app and other MCP clients through a manual config entry (see `README.md`); no packaged Desktop extension exists. User docs: `README.md`. Developer guide: `docs/README.md`. Tool reference: `docs/reference/tools.md` (generated). Design spec: `docs/superpowers/specs/2026-07-23-foundation-design.md`.

## Architecture

Flat package structure at repo root. No `internal/`. One package per responsibility:

| Package | Responsibility |
|---|---|
| `cmd/` | `main.go` entrypoint only |
| `commands/` | `urfave/cli/v3` command tree (`version`, `setup`, `mcp`, `analytics on\|off\|status`, plus the operation groups `cli.Build` makes, so far `loyalty`). `operations.go`'s `Operations(toolDeps)` builds every migrated domain service over the real sources and concatenates their `Operations()`; `Catalog()` is the same list over a zero `toolDeps`, for names, descriptions and schemas only (never run). `cli.go` mounts the CLI: `cli.Build(Catalog(), source)` makes the commands and help without opening anything, and `cliSources` opens the config store and SDE cache only when a leaf command runs. `mcp_tools.go` is the composition root for the MCP server: `NewMCPServer` builds the concrete stores, ESI clients and login flow, registers the operations with `mcp.Register(s, Operations(d))`, and registers every tool not yet migrated with one explicit `mcp.Add...` call (grouped by area in `mcp_tools_*.go`). `setup`'s keychain check prints a wait notice if it hasn't returned after 5 seconds (a locked keychain blocks on an unlock prompt, which may open on another display), and a failed check ends with an OS-specific hint (Linux: the Secret Service's default keyring) |
| `analytics/` | Anonymous usage statistics via Aptabase (one file, `analytics.go`). Two events only. `app_started`: sent once per `neat mcp` launch in a background goroutine (`commands/mcp.go`'s `startAnalytics`), carrying `appVersion`, `osName` from `runtime.GOOS`, prop `arch` from `runtime.GOARCH`, its own random session ID, and prop `monthlyId`, 128 random bits saved in `~/.neat/analytics.json` and replaced at each new UTC calendar month, so distinct IDs per month give monthly users without linking months. `tool_called`: one per tool call, recorded by `ToolMiddleware` (MCP receiving middleware added in `commands/mcp.go`, so `mcp/` and every tool are untouched), carrying only props `tool` and `outcome` (`ok`/`error`, from `CallToolResult.IsError`) under a second, separate session ID and with no `monthlyId`, so tool use can't be joined to an install. At startup `RegisteredTools` lists the server's own tool names over an in-memory session, and the middleware records only calls whose name is in that set, so `tool` is always a registered tool name, never client-supplied text. A call counts as `error` when its result has `IsError` or it ends in a Go error (e.g. output-schema validation, or a raw handler's error); the SDK can return a typed-nil `*CallToolResult` there, so check for nil before reading `IsError`. A `ToolTracker` queues them in memory (capped at 1000), flushes in batches of 25 every minute (each periodic flush on its own 5-second context, so stopping `Run` never cancels a batch mid-send) and once on shutdown (3-second timeout, after waiting for `Run` to return), and drops a batch that fails rather than retrying or persisting it. `neat mcp` turns SIGINT/SIGTERM into a cancelled context (`signal.NotifyContext`) and treats that as a clean exit, so the final flush and the SDE close still run when a client stops it with a signal. Everything is best-effort and logged only at debug level. The app key is injected via `-ldflags -X main.aptabaseAppKey`; empty sends nothing. `-X main.analyticsDebug=true` (set by the Makefile, never by GoReleaser) marks every event as Aptabase debug data, as does version `dev`, so only release builds count as users; and the key's region (`A-EU-`/`A-US-`) picks the host. Opt-out is `config.Config.AnalyticsDisabled` (`neat analytics off`, which also deletes the ID file); a nil `*ToolTracker` records nothing |
| `config/` | Non-secret state under `~/.neat/`. Shared YAML files the user can edit too, one per kind (`characters.yaml`, `facilities.yaml`, `haul_profiles.yaml`, `routes.yaml`, `structures.yaml`, `hubs.yaml`), through `yamllist.go`'s `yamlList[T]`: loads decode the file; writes (`Store.Save`/`SaveChanges`) diff what neat understood of each entry (decoded and re-encoded, so keys neat doesn't know never appear) against the new value and patch only the differing fields in the parsed document with `goccy/go-yaml`'s AST, keeping comments, order and unknown keys; a nested mapping losing keys is re-added whole; an empty or flow list is rewritten keeping its top comment; a broken file fails loads and writes with its line and is never written; writes are atomic and serialized per file in-process. Every writer changes state through `Store.Update(func(*Config) error)`, which holds one per-path lock from load to save, so concurrent writers (the login page's account controls, login callbacks, parallel tool calls) can't undo each other; a closure error saves nothing. Never `Load` then `Save` to change saved state: `Save` writes back the whole `Config`, so it's only for writing a complete state (tests). `Update` and `SaveChanges` return each `Change` (file, entry, field, old, new) for tools to report. The lock is in-process only, so two `neat mcp` processes writing at once can still lose a change. `config.json` keeps only internal state (`analyticsDisabled`, and `offeredHubIds`); `hubs.go`'s `BuiltinHubs` (the five NPC hubs, the two Perimeter markets and the Amamake Keepstar) seed `hubs.yaml` on load, each offered once so a deleted one stays deleted, best effort so a load never fails on a write; a hub is an NPC station (read from its region's order book) or a player structure (read through a character with docking access, remembered as `read_via`), with tier, traits, a dated `validation` and notes; `Store.Load` moves its old `characters`/`facilityProfiles`/`haulProfiles` sections into the YAML files once (an existing YAML file wins; a haul profile's pinned `outbound`/`return` system lists become routes named `<profile> outbound`/`return` that the profile references by name), and removes them from `config.json` only after the YAML is written. Logged-in characters carry the user's account label (`Account`: characters with the same label share an EVE account; empty means unknown, never "its own account") and `Notes` for each (`characters.go`: `UpsertCharacter` keeps both when a character is re-added; `SetCharacterAccount`, `RenameAccount`, `DeleteAccount`, `UnlabelledCharacters`, which is empty with fewer than two characters), named facility, haul and hub profiles, saved routes, and saved stations and structures (`structures.go`: kind, type, system and owner from the game, plus the user's `uses`, `facility_profile`, `clone_bay` {status yes/no/unknown, source jump_clone/user, checked date} and notes) for planning builds, routes, hauls and purchases, and the `analyticsDisabled` opt-out. Save handlers keep a profile's or route's existing name capitalization and notes when re-saved without them |
| `creds/` | OS keychain wrapper (`zalando/go-keyring`), service name `"neat"` |
| `sso/` | ESI OAuth2/PKCE login flow: state generation, a loopback browser session for the redirect (`session.go`: an HTTP server on `127.0.0.1:48211`, bound only while `add_character` runs, serving `/callback` plus a page listing the user's characters with "Add another character" and "I'm done" buttons, embedded from `sso/web/`; the page groups characters by account in compact cards (unassigned first), in a list that scrolls under a fixed header with the Add/Done buttons, and, given `AddOptions.Accounts` (an `AccountEditor`), lets the user move characters between accounts, create, rename and delete them through token-checked POSTs to `/account/set|rename|delete`; a character logged in right after another is shown in that one's account as an unsaved suggestion until the user confirms or changes it), orchestration via `github.com/fnt-eve/goesi-openapi`, refresh-token persistence via `creds/`. The redirect URI `http://127.0.0.1:48211/callback` must match the ESI application's registered callback URL exactly, so the port is fixed. The session ends when the user clicks Done, closes the tab (a `pagehide` beacon, backed by a 30-second ping timeout), or a login gets no callback within 5 minutes; it accepts only its own `Host` header (DNS rebinding) and a per-session page token on every POST (CSRF), and each OAuth2 state is single-use. `scopes.go` defines the scope groups a login can request (`ScopeGroups`; `basic` always, the rest chosen per login, so no login asks for all 72 scopes at once) and `GrantedScopes`, which reads a character's granted scopes from its current access token's `scp` claim. All outbound requests to FC (JWKS fetch, OAuth2 token exchange) carry `sso.UserAgent(version)`, per ESI's User-Agent best practices. Also caches a per-character auto-refreshing HTTP client (`AuthenticatedClient`/`RemoveCharacter`) for `esi/`'s use — refreshing relies entirely on `golang.org/x/oauth2`'s own token source (with rotated refresh tokens persisted back to `creds/` if FC ever returns one), not hand-rolled expiry tracking. `AuthenticatedClient`, `RemoveCharacter`, and `add_character`'s token save share one mutex across their entire keychain operation, not just the cache map, so none can interleave. Re-adding an already-known character (e.g. after FC revoked its refresh token) evicts that character's cached client along with saving the new token, so the fresh login takes effect immediately rather than after a process restart |
| `mcp/` | MCP server (official `github.com/modelcontextprotocol/go-sdk`) and its 277 tools. `register.go`'s `Register(server, ops)` registers each migrated `operation.Operation` with the SDK's low-level `AddTool`, its schemas and input validation coming from `operation`; every tool not yet migrated is still registered by an exported `Add...` function that `commands/mcp_tools.go` calls with the concrete config store, SDE cache, ESI client and login flow it built (each tool file declares small interfaces for exactly what it uses and never names `esi.Client`, `sde.Store`, `config.Store` or an `sso` function; `add_character.go` shows a login flow reached through its own `characterLogin` interface, with `commands/mcp_tools_admin.go` implementing it over `sso`). `server.go`'s `NewServer(version)` returns a server that carries the instructions and no tools; there is no `Deps`, `ConfigStore` or `SDEStore`. See `docs/superpowers/specs/2026-11-25-consumer-interfaces-design.md` (the navigation, hauling, trade hub, purchase and industry planning tools are converted too: `planner.go` is a consumer that declares its own `plannerClient`, `plannerPublicClient`, `plannerConfig` and `plannerSDE` interfaces, and each of those tools' generic `Add...` functions takes the clients' openers and makes the planner's non-generic ones with `plannerOpener` and `plannerPublicOpener`; the ESI functions several files call, such as `listAssets` or `getUniverseStructure`, are plain functions taking the small interface declared beside them). The full list, grouped by player-facing area, is `docs/reference/tools.md`, generated by `tools/gentooldocs` from a live `commands.NewMCPServer` (`go generate ./...`); its test fails while that file is stale, and generation fails if a new tool matches no area in `tools/gentooldocs/main.go`'s `areas` (an area must come before any whose keywords its tools also contain, e.g. killmails before mail). `instructions.go` holds `Instructions`, sent to every client in the initialize result: onboarding (`list_characters` → `list_scope_groups` → `add_character`, always offering the corporation groups and adding `structures` for assets or industry, plus the `http://127.0.0.1:48211/` fallback when no browser tab opens), scope errors, corporation tools refused for in-game roles (try one other character in the corporation, never every one, to spare ESI's error limit), adding a group to several characters in one login, confirming before write tools, never computing industry numbers, and the order for planning a move (overview, inventory, ships and pilots, routes and their checks, lighters, jump clones). It's the only guidance clients without plugin skills (e.g. Claude Desktop) get, so keep it consistent with the skills. Notable tools: `add_character` (one call can add several characters through the browser session page; returns them all; grants the `basic` scope group plus the `scopeGroups` asked for, and with `characterId` re-authorizes a character keeping its granted scopes, returning `warnings` if the user logged in as someone else or the old scopes couldn't be read). `readiness.go` holds `list_character_capabilities` (cynos, bridges and conduits each character can use and on which hulls, and flyable hauling, jump and capital hulls by class, all from SDE requirements and the character's skills) and `list_jump_clones` (jump clones with implants, the current clone's implants as `activeImplants`, home station, cooldown and next clone jump from Infomorph Synchronizing, capacity, and `jumpFromHere`: whether a clone jump can start where the character is docked, yes when any logged-in character has a jump clone there or `structures.yaml` says yes, no when it says no, otherwise unknown or not_docked; `readyNow` needs both `cooldownReady` and yes, and the overview reports the same), naming structures from `structures.yaml`. `haul_ships.go` holds `list_haul_ships`: every assembled ship in a `hullClassGroups` class, or of any other class with a cyno generator fitted (`cyno ship`), across the characters' and optionally a corporation's assets, each with owner, item ID, class, name, the station, structure or system it's in (`rootOf` follows containers and ship bays up, naming the carrying ship) with displayed security, and its fitted generator; a corporation's ships carry their fitted modules instead of an owner, since `resolveShip` reads only a character's assets. `plan_jump_route` adds `checks` per route (`nav.CheckLandings` against `structures.yaml`, `nav.FuelFit` against the hull's fuel bay) and `cynoTypes`; highsec entry comes from the hull's `disallowInHighSec` SDE attribute, so the navigation tools no longer depend on `industry/`. `plan_haul` takes `with` (more haul profiles): `haulPlanWith` routes for the first ship, validates every other ship on the same systems, packs loads for the combined hold and splits each with `cargo.SplitLoad`, merging fuel into the Multibuy and reporting `sharedCynoTypes`. `ship_tools.go` holds `estimate_ship_hold` (every hold base and fitted, cargo used and free, fitted warp, speed and align, and jump range and fuel by the same math as `plan_jump_route`, for a ship read from assets by `shipItemId` or a hull and modules by name) and `estimate_cyno` (fuel per light, cycle, lights per load, whether the generator fits, the lighter's missing skills; the generator's own fuel already in the cargo hold isn't counted against the hold, and `loads` (from `nav.CynoFuelLoads`) lists every load of fuel the lights take, before which light and how many units to add, with `fills` its length: an owned ship starts from the fuel aboard, `fuelAboard`/`lightsAboard`, and a ship given by name from an empty hold); `save_haul_profile` takes `shipItemId` to derive the hold. `hulls.go` holds `compare_haul_hulls` (per hull: holds from `cargo.Holds`, `nav.DescribeHull` facts, fuel, and with a pilot whether they can fly it and their jump range and fuel). `overview.go` holds `get_logistics_overview`: per character, six ESI reads in parallel (location, ship, online, clones, fatigue, skills; they share no planner state), then account label, online, location with displayed security, ship, abilities, flyable hull classes, clone readiness and fatigue, naming each part ESI refused in `unread`; plus account groups and conflicts (characters labelled alike online at once). `hubs.go` holds the hub tools: `hubBooks` reads a hub's sell orders for every pricing tool (`quote_market_purchase`, `plan_build`, `solve_ore_mix`, `plan_haul`), from the region for an NPC station or from the structure's market through `planner.marketCharacter` or the hub's `read_via` character, never trying characters blindly; `validate_trade_hub` scores a hub on `market.DefaultBasket` (24 everyday goods) or a given basket and optionally its public contracts by value band with the ship groups in the priciest, and records the dated result; `compare_trade_hubs` ranks hubs for a shopping list with `market.RankHubs` and gate jumps from `nav.RouteGraph.GateJumps`; list/save/delete hub profiles; a validation over 30 days old is reported stale. `saved_structures.go` holds `list_structures` (records a clone bay as yes/jump_clone, with the date, wherever any logged-in character has a jump clone, overriding the file and reporting the change; never records a missing bay from a missing clone; checks docking access live per requested character by trying the structure lookup), `save_structure` (fills name, kind, type, system and owner from the SDE for NPC stations or from ESI through a character with docking access for Upwell structures, keeping saved facts with a warning when no character is given; takes the user's uses, facility profile, a clone bay they checked as source user, and notes) and `delete_structure`. Write tools (`respond_calendar_event`, `add_/update_/remove_character_contacts`, fittings, fleet, mail, `set_autopilot_waypoint`, `open_*_window`) use verb-first names, say in their descriptions that they change state on EVE's server, and take no confirmation parameter. The planning tools call the pure packages below: haul profiles, `plan_jump_route` and `plan_haul` call `nav/` and `cargo/`; hub profiles and `quote_market_purchase` call `market/`; the industry tools (`save_/list_/delete_facility_profile`, `describe_facility`, `calibrate_facility_profile`, `find_owned_blueprints`, `check_build_skills`, `check_material_stock`, `estimate_*`, `solve_ore_mix`, `plan_build`) call `industry/`; the profile writers change only `~/.neat/config.json`, and `plan_build` saves its full plan under `~/.neat/plans/`. `mcp/enrich.go` holds `resolveTypeNames`, the shared SDE-backed `type_id` → name resolver that populates the `*Name` sibling fields (`TypeName`, `ShipTypeName`, ...) alongside the bare `*ID` fields ESI returns, across 44 tools in 19 non-Universe files (`assets.go`, `contracts.go`, `killmails.go`, `market.go`, `industry.go`, `wallet.go`, ...). It deduplicates IDs per call and drops failed lookups rather than erroring — enrichment is additive, so one bad ID must never fail a tool call over data ESI already returned. Batch 2 extended `mcp/enrich.go` with six sibling resolvers (`resolveSystemNames`/`resolveRegionNames`/`resolveConstellationNames`/`resolveStationNames`/`resolvePlanetNames`/`resolveMoonNames`) covering the same additive-`*Name` pattern for system/region/constellation/station/planet/moon IDs across 14 more files. Batch 3 further extended `mcp/enrich.go` with four sibling resolvers (`resolveRaceNames`/`resolveBloodlineNames`/`resolveFactionNames`/`resolveGroupNames`) covering the same additive-`*Name` pattern for race/bloodline/faction/group IDs across 8 more files, closing out batch 1's originally-flagged follow-up list. The Wallet tag's two wallet-transactions tools (`list_character_wallet_transactions`/`list_corporation_wallet_transactions`) adopt the same `TypeName` enrichment via `resolveTypeNames`, bringing `wallet.go` into the enriched-file set for the first time. The Cosmetics tag adds two SDE-only sibling resolvers, `resolveSkinrComponentNames`/`resolveSkinrSlotNames`, enriching `get_skinr`'s slots and `list_character_skinr_component_licenses` with component and slot names (alongside `get_skinr`'s `ShipTypeName` via `resolveTypeNames`). |
| `operation/` | The contract between domain services and adapters, with no logic of its own: `Operation` (name, description, `Kind` `Read` or `Write`, input and output `reflect.Type`, `Run`), built by `New[In, Out]`, which derives the input and output JSON schemas exactly as the SDK's typed `AddTool` does (and panics, as `AddTool` would, on a type it can't derive, such as a self-referential one). `Decode` validates and decodes caller input against the input schema, wrapping `ErrInvalidInput` so adapters can tell bad input from a failure; `EncodeOutput` validates output against the output schema as the SDK's typed handler does |
| `character/` | Domain: which characters neat has logged in. `Known(store, characterID)` is the one logged-in check, shared by domain packages and the MCP character tools; `ErrNotFound` is its sentinel |
| `universe/` | Domain: lookups over New Eden's static universe data. So far `TypeNamer` (`NewTypeNamer(sde, userAgent)`), the SDE-only type-name resolver behind the additive `TypeName` fields, which drops misses and never calls ESI (the additive-enrichment exception; `mcp/enrich.go`'s `resolveTypeNames` now delegates to it) |
| `loyalty/` | Domain: loyalty point balances per corporation and what a corporation's loyalty store offers. The worked example of a migrated area: `loyalty.go`'s `Service`, built by a generic `New` over ESI openers, the character registry and a type namer through interfaces it declares itself, exposes `list_character_loyalty_points` and `list_loyalty_store_offers` as `Operations()`. Its input and output types carry no ESI model (`commands/operations_test.go` checks every operation) |
| `cli/` | Adapter: builds the CLI's command groups from operations. `Build(describe, source)` makes one leaf per operation at its `Paths` entry (`paths.go`: the hand-maintained table of operation name to command path, plus `Groups`, each group's one-line help; the only place command naming lives); flags come from the input struct's `json`/`jsonschema` tags (kebab-case, a scalar's trailing `Id` dropped: `characterId` → `--character`; slices are repeatable), with `--json '{...}'` or `--json -` for the whole input and `--pretty` to indent. Output is compact JSON on stdout; errors are `{"error": "..."}` on stderr with exit 1, or exit 2 for bad input. `source` builds the real operations only when a leaf runs, so `--help` touches nothing. Imports only the standard library, urfave/cli and `operation` |
| `nav/` | Pure calculations for moving ships and characters through New Eden, for any activity (PvP, PvE or industry), not only builds — no network, disk or clock access, and no other neat imports; `mcp/nav_*.go` gathers SDE, ESI and config inputs and calls it. Security bands (highsec, lowsec, nullsec incl. Pochven/Zarzakh, wormhole), the displayed security value and its in-game color (`SecurityOf`, carried on every route leg and on `get_universe_system`), and where a cyno can be lit; jump fuel, range and fatigue (EVE's 9.46e15 m light year, fuel rounded per jump — matches dotlan to the unit); jump/gate route search with pilot preferences (`MaxGates` is a `*int`: nil is no limit, 0 is no gates, and a pinned route over it is flagged) and dotlan links; `cyno.go`'s `CynoFuelLoads` lays out each cyno fuel top-up. `capabilities.go`: whether skills meet a type's requirements (`Trained`, `Missing`), which hulls a character can fly, and `Abilities`, which decides each cyno, bridge and conduit ability from the module's required skills and the hulls it fits (both read from the SDE by `mcp/readiness.go`: `requiredSkillN`/`requiredSkillNLevel` and `canFitShipGroupNN`/`canFitShipTypeN` attributes, plus hulls with the `jumpPortalPassengerBonusModAddSkill` effect for the carrier conduit); clone jump cooldown, next clone jump and jump clone capacity. `hull.go`: `DescribeHull` (warp speed, align estimate, warp core strength, cloak and nullification from the cloak's and nullifier's SDE fitting restrictions or the hull's nullification effect, highsec entry from `disallowInHighSec`, jump drive, and the bridges and conduits it can ride from the `is…Passenger` attributes), `DockingFor`/`CanDock` (capital docking by ship group, matching faction structure variants by base name) and `CynoTypesFor`. `landings.go`: `CheckLandings` (per jump leg: cyno types, where the hull can dock among NPC stations and saved structures, gates a single lighter travels from the previous landing), `SharedCynoTypes` for ships flying together, and `FuelFit` (route fuel against the fuel bay). Every number the SDE doesn't carry is a sourced constant in `nav/constants.go` (including the generator type IDs, which generators also conduit, the clone rules, capital docking per class, and which jump drives use industrial and covert cynos). Design: `docs/superpowers/specs/2026-11-20-logistics-planning-design.md` |
| `cargo/` | Pure calculations for what fits where — no network, disk or clock access, and no other neat imports: a hull's holds by base capacity from its SDE attributes (`holds.go`); item volumes (assembled for a singleton, packaged otherwise); `Inventory`, which lays out everything at one station or structure in tree order (corporation offices transparent, and modules, service modules, quantum core and deed fitted to the structure itself left out) with each assembled ship's assembled and packaged volume, what comes out of it to repackage it and the rigs that destroys (strategic cruisers keep theirs), and totals for a move (backs `list_location_assets`, which also totals each owner's share in `sources`; output is a flat list with `parentItemId`/`depth`, since MCP output can't be self-referential); packing a cargo list into loads that fit a hold, each an even slice of everything; `SplitLoad` divides a load between several holds flying together, in proportion and keeping portions whole. Constants in `cargo/constants.go`. Design: `docs/superpowers/specs/2026-11-20-logistics-planning-design.md` |
| `market/` | Pure buying calculations for any purchase, not only build materials — no network, disk or clock access, and no other neat imports; `mcp/market_*.go` calls it: walking a sell order book for a quantity at a station, in-game Multibuy lists, and trade hub scoring (`hubs.go`: `ScoreBasket` on `DefaultBasket`, `BandContracts` by value, and `RankHubs` for a shopping list). Design: `docs/superpowers/specs/2026-11-20-logistics-planning-design.md` |
| `dogma/` | Pure dogma evaluator for a ship, its fitted modules and its pilot's skills — no network, disk or clock access, and no other neat imports: each attribute starts from its SDE value (or default) and every modifier of every applicable effect (passive, plus online for modules; the generic `skillEffect` skipped, since skill levels are set directly) is applied in the game's operation order, with stacking penalties for modules on non-stackable attributes (an attribute with no info counts as stackable; an `Item` marked `Unpenalized`, which `mcp/fitting.go` sets for subsystems, is exempt); domains `itemID`, `shipID` (`ItemModifier`, `LocationModifier`, `LocationGroupModifier`, `LocationRequiredSkillModifier`) and `charID` `OwnerRequiredSkillModifier`; evaluation is lazy and memoized, with cycles falling back to base values. Matches the game on worked figures (Ark 263,351.25 m³; cyno Venture 96.96 m³ and 240/200 ozone at CFT IV/V; Falcon 50 ozone, 5-minute cycle). `mcp/fitting.go` builds fits from `sde.DogmaTypes` (which seeds attributes 4 mass and 38 capacity from `invTypes` columns) and `sde.AttributeInfos` |
| `industry/` | Pure industry calculations — no network, disk or clock access; `mcp/industry_*.go` gathers SDE, ESI and config inputs and calls it. Imports `nav/` (security bands) and `market/` (order books); neither imports it, nor does `cargo/`, so nothing about moving or buying depends on industry. Facility bonuses resolved from the SDE's own `indModifierSources`/`indTargetFilters` tables and dogma attributes for every facility kind (NPC station, Upwell structure, starbase) in every security band; per-job material rounding, job time, job fees (or a calibrated rate), ME/TE research, copying and invention; blueprint tree expansion with build/buy decisions, owned copies and stock netting; build-vs-buy; Upwell and NPC reprocessing yield; the compressed-ore linear program (`gonum.org/v1/gonum/optimize/convex/lp`); job scheduling across builders. Every number the SDE doesn't carry is a sourced constant in `industry/constants.go`. Design: `docs/superpowers/specs/2026-11-18-industry-planning-design.md` |
| `esi/` | Thin facade over `github.com/fnt-eve/goesi-openapi`. `NewClient` builds a per-character authenticated ESI API client from `sso.AuthenticatedClient`'s cached, auto-refreshing HTTP client; `NewClient` also checks every request against `scopes_gen.go`, a table of each ESI endpoint's required scope ("" for public ones) generated by `tools/genscopes` from the OpenAPI spec bundled in `goesi-openapi` (`go generate ./esi/`; rerun after bumping it). A request for an endpoint whose scope the character's access token doesn't carry fails before it is sent with `*esi.MissingScopeError`, whose message names the scope group and tells the agent to re-authorize via `add_character` with `characterId` and `scopeGroups`; the most specific template wins, so public endpoints are in the table too. `NewPublicClient` builds an unauthenticated client for resource groups where every endpoint is public (e.g. Alliance — no character needed at all). Holds no state of its own. Covers one ESI resource group ("tag") per file (`wallet.go`, `access_list.go`, `activities.go`, `alliance.go`, ...) — see `docs/reference/esi-coverage-roadmap.md` for what's covered and what's left across all 39 tags (the original 36, plus Military Campaigns, Cosmetics, and Paragon Hub, all implemented since goesi-openapi v0.0.42 / compatibility date 2026-08-18). `esi.AllPages` walks every page of any paginated call. |
| `sde/` | Local cache of fuzzwork.co.uk's periodically-refreshed SQLite conversion of FC's Static Data Export (`~/.neat/sde/eve.db`), queried directly via `database/sql` + `modernc.org/sqlite` — no intermediate key-value store. ## Hard rules

- **Prefer a cached, statically-refreshed source over a live per-request ESI call**: any tool needing a resource available from FC's SDE or from EVE Ref's `esi-scrape` bulk export must read it from `sde/`, never call ESI for it directly. Performance and API-citizenship requirement, not a suggestion. `sde/` is backed by a single downloaded file — fuzzwork.co.uk's SQLite conversion of FC's SDE, ETag-checked and re-downloaded once per process lifetime on change (sync-fatal on failure) — queried directly via SQL, no intermediate key-value store. Three fields with no source in that file come from narrow fetches against EVE Ref (best-effort — a fetch or parse failure there logs a warning and falls back to the last saved values, or skips that field's augmentation if none were saved, never failing the rest of the sync): race `AllianceID` and graphic `SofDNA` from the `esi-scrape` dataset, and type `Radius` from the `reference-data` dataset. Type `Radius` moved there in the 2026-11-18 audit, when fuzzwork dropped `invTypes.radius`; until `sde/type.go` stopped selecting it, every `Type` lookup failed with "no such column: radius", which broke `get_universe_type` outright and silently blanked every `TypeName` enrichment. Type `PackagedVolume` was sourced from `reference-data` too, until FC added it to the SDE itself (https://github.com/esi/esi-issues/issues/1499) and fuzzwork's dump picked it up as a plain `invTypes.packagedVolume` column — `sde/type.go`'s `Type` reads it straight off that column, same as `mass`/`volume`/etc. 24 of the Universe tag's 30 tools are `sde/`-backed via a read-through cache: try `sde/` first, fall back to a live ESI call on a cache miss, write the result back (into a process-lifetime in-memory overlay, not the downloaded file, which is treated as read-only) so the next lookup of that ID is fast. The other 6 (`list_universe_structures`/`get_universe_structure`, `list_universe_system_jumps`/`_kills`, `resolve_universe_ids`/`_names`) are permanently ESI-direct by design -- they resolve live, non-cacheable data (structures are player-owned and access-gated; jumps/kills are moment-in-time activity counters; the resolve tools take arbitrary caller-supplied names/IDs), not an SDE sourcing gap. Four fields have no source anywhere in the fuzzwork dump: `get_universe_graphic`'s `CollisionFile` (also absent from EVE Ref's `esi-scrape` mirror of ESI's own live responses -- unaffected by the sqlite migration), `get_universe_region`'s `Description` (`mapRegions` has no description column at all -- a genuine regression from the prior bbolt design, which sourced it from FC's own jsonl), `get_universe_station`'s `Services` (`staOperationServices` has zero rows in the dump), and `list_universe_factions`'s `IsUnique` (`chrFactions` has no `uniqueName`-equivalent column). Each is populated on a cache miss (fresh off ESI) but not on a cache hit -- documented in `docs/superpowers/specs/2026-08-04-sde-sqlite-migration-design.md`'s field-drop findings. The `reference-data`/`esi-scrape` archives (about 57 MB and 77 MB) are gated too, but not by HEAD: data.everef.net sends no ETag, and its Last-Modified is Cloudflare's edge cache-fill time, which differs between requests. Each `sync()` instead reads the dataset's `index.json` (a few hundred bytes), whose per-file `etag` is the origin's own, and downloads an archive only when that etag differs from the one saved in `~/.neat/sde/everef.json` with the extracted values (`sde/everef.go`). If the index can't be read, the archive is downloaded as before; if that download fails, the saved values are used.
- **Industry bonuses come from the SDE, not code**: structure role bonuses, rig bonuses and each rig's own security multipliers, which products each rig or structure affects (`indModifierSources` + `indTargetFilter*`), refinery yield bonuses, implant bonuses and jump drive attributes are all read from the fuzzwork dump at use time. The only numbers kept in code are those with no SDE source, each a named constant in its package's `constants.go` citing where it comes from: `industry/constants.go` (SCC surcharge, Alpha tax, tax cap, NPC facility tax, reprocessing base and rig/security terms, invention base chances and decryptors, research level durations) and `nav/constants.go` (the light-year constant, jump fatigue limits). Facts ESI can't see (fitted rigs and services, owner taxes, hauling hull and routes, routing preferences) live in saved profiles and routes in `~/.neat/`'s YAML files, never as hard-coded assumptions.
- **Logins request scope groups, never every scope**: `add_character` asks FC for the `basic` group plus the groups the user picked (`sso/scopes.go`), and a tool needing more fails with `esi.MissingScopeError` until the user re-authorizes. Requesting all scopes in one login pushed FC's login-site cookies past its request-header limit after a couple of logins ("HTTP Error 400. The size of the request headers is too long"). Every scope an ESI endpoint needs must belong to exactly one group; `esi`'s and `sso`'s tests enforce it, so a `goesi-openapi` bump that adds an endpoint with a new scope fails CI until the scope is grouped.
- **Analytics send nothing that identifies a person or machine**: `analytics/` sends exactly two events. `app_started` carries only the version, the build's `runtime.GOOS`/`runtime.GOARCH`, its session ID and the monthly random ID. `tool_called` carries only the registered tool name and `ok`/`error`, plus version and OS name, under a separate session ID and never the monthly ID. Never add character IDs or names, tool arguments, results, error text, durations, paths, hostnames, locale, OS version, hardware identifiers or any persistent ID to either, never put the monthly ID or `app_started`'s session ID on `tool_called`, never make the monthly ID outlive its month, and never write queued events to disk. Any change to what is sent changes `PRIVACY.md`'s "Anonymous usage statistics" section in the same commit. Users opt out with `neat analytics off`; that must stay one command and must stop all sending.
- **No environment variables for config/credentials.** Config lives under `~/.neat/`; credentials
  live in the OS keychain only.
- **No client secret.** The ESI app is a PKCE-only public app — nothing secret ships in the binary.
- **ESI User-Agent compliance**: every outbound request to FC's login/ESI endpoints must carry `sso.UserAgent(version)`. FC's best-practices guidance treats non-compliant User-Agents as grounds for a temporary ban — see `sso/useragent.go`.
- **ESI error detail must not be discarded**: every `esi/` method that calls `.Execute()` on a generated API request must route its error and `*http.Response` through `describeError` (`esi/error.go`) before wrapping and returning it. `goesi-openapi`'s generated error type degrades to a bare HTTP status string on its own — its message formatter looks for `Title`/`Detail` fields via reflection, but ESI's actual error model uses `Error`/`Details` instead, so the real detail (invalid scope, expired token, etc.) and the `X-Esi-Error-Limit-Remain`/`-Reset` rate-limit headers are silently lost unless routed through this helper. Confirmed via direct reproduction against `goesi-openapi` v0.0.37 — see `esi/wallet.go` for the pattern every new `esi/` method should follow. When no ESI error detail can be extracted, notably when a 2xx response fails to decode into the generated model, `describeError` appends the raw response body (truncated to 512 bytes) instead, so the error shows what ESI actually sent rather than only what the model expected.

- **Developer License Agreement notice is verbatim**: the end of `README.md`, the end of `PRIVACY.md` and the footer of `sso/web/page.html` carry the proprietary notice from section 7.1 of https://developers.eveonline.com/license-agreement exactly as the agreement words it, including "CCP hf.". It is the one place the old company name stays: elsewhere use Fenris Creations in introductory text and FC everywhere else. Change its wording only if the agreement's own text changes.

## Conventions

- Wrap errors with context: `fmt.Errorf("operation: %w", err)`. Never discard an error (`_ = err`).
- External test packages by default (`package foo_test`); use `*_internal_test.go` only when a
  test genuinely needs an unexported symbol.
- Table-driven where a table naturally fits (many input variations on one code path);
  independent, clearly-named tests otherwise — don't force behaviorally distinct scenarios into
  one table just to have a table. Standard library only, either way — no `testify` or other
  assertion libraries.
- `creds/` tests must call `keyring.MockInit()` before touching keychain functions — never let
  tests hit the real OS keychain.
- Never model a nested/tree-shaped ESI resource with a self-referential Go struct (a type whose
  field is `[]ThatSameType`). It passes `go build`/`go vet`/`gofmt` but panics at server startup
  ("cycle detected for type ...") in the MCP SDK's output-schema generator — only `go test ./...`
  actually calling `mcpsdk.AddTool` catches it. Instead, define one distinct, non-recursive type
  per real nesting level, matching the ESI schema's actual depth (see `mcp/killmails.go`'s
  `KillmailItem`/`KillmailInnerItem` split).

## Go standards

These standards bind **new and changed code**. The existing code predates them and is brought into line later, so a violation you did not touch is not a reason to refactor it in an unrelated change. Where neat departs from the strict form of a standard, the departures are listed at the end.

- **Errors are handled, never dropped.** No `_ = f()`, no ignored return values, no empty `if err != nil {}`, including `Close`, `Remove`, `Flush` and deferred cleanup. A cleanup error on a path that is already returning an error is joined into it (`errors.Join`, with a named return), not discarded.
- **Every error passed up is wrapped with context** that says what was being done and to what (character, tool, path, ID): `fmt.Errorf("<what>: %w", err)`. Use `%w` whenever the cause should stay inspectable with `errors.Is`/`errors.As`; where `%w` is not possible the message must stand on its own. Add context at each layer boundary without stuttering.
- **The caller decides.** Lower layers return errors and never log-and-continue or pick policy; errors travel up to the outermost layer (`cmd/main.go`, an MCP tool handler), which reports them and maps the exit code. Command handlers return plain wrapped errors for runtime failures and `cli.Exit` only to carry a different exit code (usage errors, 2); `cli.Exit`'s error has no `Unwrap`, so it holds a standalone message, not a cause callers inspect.
- **A loop that must continue past one failing item collects with `errors.Join`** and returns the joined error rather than printing and swallowing it.
- **Callers that must branch on a failure get an exported sentinel or typed error** from the package. Any intentional exception to the rules above carries a comment saying why.
- **No fallbacks in new code.** Code succeeds explicitly or returns an error the caller wraps: no best-effort matching, no silent degradation, no fail-open path. The best-effort behaviors neat already documents are the only exceptions, and each stays confined to its place: analytics, the EVE Ref augmentation fetches in `sde/`, the read-through ESI fallback on an `sde/` miss, `sde/`'s lookups answering from the cache on disk when a sync fails (`syncBestEffort`, which drops the error `ensureSynced` already logged), the additive `*Name` enrichment (`mcp/enrich.go`), and `config`'s seeding writes on load. A new best-effort path needs the same written justification beside it and an entry here.
- **Consumer-defined interfaces.**
  1. The package that **uses** a capability declares the small interface it needs, in that package, named for the use.
  2. Producer packages (`sde`, `esi`, `sso`, `creds`, `config`, `analytics`) export concrete types and no interfaces meant for their callers. The pure calculation packages (`nav`, `cargo`, `market`, `dogma`, `industry`) take plain data and need none.
  3. Interfaces are as small as the consumer's actual calls. Accept interfaces, return structs. The value passed in may have far more methods than the interface lists: a consumer that only calls `Do` declares `type doer interface{ Do(*http.Request) (*http.Response, error) }` and is handed an `*http.Client`, with no mirror interface of the producer's whole API and no pared-down wrapper. Callers pass the concrete value as it is. Likewise a consumer may declare such an interface in the file that first uses it and reuse it from other files in the package.
  4. A command's code contains no system-specific branching; a resolver wires the implementer.
  5. Test seams are the interfaces; fakes live in the `_test.go` files of the consumer, not in the producer.
  6. Define a type in the same file as the code that uses it. A file that exists only to declare types, including any `*_iface.go`, is not allowed.
  7. Factories return an untyped `nil, err`, never a typed nil inside an interface.

  `go run ./tools/ifaceaudit` lists the departures (`CONCRETE_PARAM`, `CONCRETE_CTOR` for any `New*`/`Open*` call on a producer outside a composition root or a `*test` fixture package, `PRODUCER_IFACE`, `INTERFACE`, `IFACE_AWAY` for an interface declared in a file that never uses it while another file in the package does, which a deliberately shared interface avoids by being used where it is declared, and `TYPE_ONLY_FILE`). The repo now conforms: CI fails on any `CONCRETE_PARAM`, `CONCRETE_CTOR`, `PRODUCER_IFACE`, `IFACE_AWAY` or `TYPE_ONLY_FILE` (`TestRepoConformsToConsumerInterfaceRules` in `tools/ifaceaudit/main_test.go`, which runs with `go test ./...` in the existing test workflow; `TestEnforcedKindsFailOnViolations` proves each enforced kind is detected, so the gate can fail; the audit skips `_test.go` files), so a change must add none. Only `INTERFACE`, the list of every interface and who uses it, stays informational; an unexported interface in a producer package is internal and reported as `INTERFACE`, not `PRODUCER_IFACE`.
- **Tests: fix the API, not the test.** A unit test runs from outside the package it tests (`package foo_test`) and imports it like any caller. If a behavior or error path can only be tested from inside, the exported API is deficient (a missing error value, an unexported failure mode, a missing option): fix the API. `*_internal_test.go` is for the rare case where an unexported symbol is the thing under test (a generated schema, a parser's internals), never to reach past an API that should have exposed what the test needs. Put new tests in the `{x}_test.go` that matches `{x}.go`, rather than a new file per scenario. Tests never touch the real keychain, the real `~/.neat/` or the network; use `t.Setenv("HOME", t.TempDir())` and fakes.
- **Tests are required for new behavior** and for everything that decides whether to call ESI, start a login or write state: scope checks, the SDE-versus-ESI routing, config writes and their lock, and the pure calculation packages. Do not leave an untested code path in anything security-sensitive.
- **Formatting and hygiene** are checked in CI and by `.claude/settings.json`'s hooks: `gofmt` clean, `go mod tidy` and `go generate ./...` leave no diff, `go vet` passes. `go fix ./...` leaves no diff too (a CI step and the Stop hook run it).
- **GitHub Actions:** third-party actions are pinned to a full commit SHA with a `# vX.Y.Z` comment (resolve with `gh api repos/<owner>/<action>/git/ref/tags/<tag>`, dereferencing annotated tags). Untrusted input (PR title, body, branch names) is never interpolated into `run:` steps. New workflows follow this now; the existing ones still use version tags and are pinned in the cleanup.

Departures from the strict form of these standards: the "lower layers never log" and "no fallbacks" rules keep the best-effort exceptions above; "one `{x}_test.go` per `{x}.go`, no `_internal_test.go`" is a preference here, because 100+ internal tests exist; prod-safety and version-gate rules are covered by the Hard rules above and `tools/versiongate`; and neat has no required `CI / build` aggregate check yet.

## Keeping docs & Claude resources in sync

`neat` is consumed by both humans and agents through several surfaces that must not drift from the
code. **When a change affects behavior, update the relevant surfaces in the same commit/PR** —
treat it as part of "done," not a follow-up:

- **User docs** → `README.md` is for EVE players, not developers: what neat is, example questions, install (release binary, Claude Code plugin, Claude desktop config), choosing scope groups, where data lives, troubleshooting, and a short Development section. Keep big tables and implementation detail out of it; they belong in `docs/README.md`, `docs/reference/` or this file. Update it when installation, login, scope groups, data locations or user-visible errors change. It ships inside every release archive, so it must stand alone.
- **Packages / architecture** → the package table and conventions in **this `CLAUDE.md`**, and the package list in `docs/README.md`. Note significant departures from `docs/superpowers/specs/2026-07-23-foundation-design.md` in that spec's own status line rather than rewriting it — it's a historical record of what was decided, not a living doc.
- **MCP tools** (added, renamed or redescribed) → run `go generate ./...` to regenerate `docs/reference/tools.md`, placing any new tool in an area in `tools/gentooldocs`. Tool counts appear only in that generated file and this file's `mcp/` row; keep counts out of `README.md` and the plugin and marketplace manifests, which drift.
- **Server instructions** (`mcp/instructions.go`) → when onboarding, scope handling or write-tool behavior changes, update them alongside the skills that cover the same ground.
- **CLI surface** (new command, flag, or exit-code contract) → `README.md`'s install steps, `docs/README.md`, and this file's package table.
- **Credentials** (new keychain key, service name, or verification flow) → `creds/`,
  `commands/setup.go`, and the Hard rules / Conventions sections here.
- **Hard rules** (SDE-vs-ESI routing, no client secret, no env vars for storage) → keep these
  listed here exactly as they're enforced in code; if a rule is relaxed or tightened, this file
  changes in the same commit as the code that changes it.
- **Plugin skills** (`claude_resources/neat/skills/*/SKILL.md`: `add-character`, `industry-build-plan`, `industry-profile-setup`, `haul-plan`) → when `add_character`'s or an industry, hauling or routing tool's inputs, outputs or behavior change, or a scope group changes, update the skill that drives it in the same commit. Skills hold discovery and decision steps only — never formulas or arithmetic.
- **Plugin packaging** → `claude_resources/README.md` (developer-facing: contents, skills, testing a local build), `claude_resources/neat/CHANGELOG.md` (user-facing release notes, one entry per `VERSION`), and the descriptions in `claude_resources/neat/.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`.
- **Review rules** → `.claude/review.md`, the checklist a reviewer (human or Claude) applies to a PR. Keep it short; the rules themselves live in "Go standards" and "Hard rules" here, and `.claude/settings.json` holds the shared hooks (`.claude/settings.local.json` is per-user).
- **Agent-facing surfaces that don't exist yet** — once built in a later plan, add them to this list: a packaged Claude Desktop extension (`extension/manifest.json`), which would replace the README's manual desktop config. Don't leave a plan's own doc updates (e.g. its plan file, or a spec status line) as a "follow-up" task.

## Build

`clientID` (the ESI OAuth2 client ID, `esiClientId`) and `aptabaseAppKey` (optional; empty sends no analytics) are injected via `-ldflags` from the git-ignored `app_config.json` — `make build` wraps this for local development. Releases read them from the `ESI_CLIENT_ID` and `APTABASE_APP_KEY` repository variables.

```bash
go build -ldflags "-X main.version=$(cat VERSION 2>/dev/null || echo dev) -X main.clientID=$(jq -r '.esiClientId // .clientId' app_config.json) -X main.aptabaseAppKey=$(jq -r '.aptabaseAppKey // ""' app_config.json) -X main.analyticsDebug=true" -o neat ./cmd
```

`make install` builds and installs `neat` to `~/.local/bin` (override with `PREFIX=...`). It removes the old binary before copying the new one, because on macOS copying a build over an existing binary in place makes the kernel kill it on launch (exit 137); if you install by hand, `rm` first.

```bash
make install
```

## Versioning & Release

The top-level `VERSION` file is the single source of truth for the `neat` binary version, the Claude Code plugin manifest version, and the release git tag. `tools/genversion` (wired via `go:generate` in `cmd/main.go`) propagates it into `claude_resources/neat/.claude-plugin/plugin.json` — run `go generate ./...` after bumping `VERSION` and commit the result.

`tools/versiongate` is a required PR check: any PR touching release-significant files (Go source, `go.mod`/`go.sum`, `.goreleaser.yaml`, anything under `claude_resources/`) must bump `VERSION`. Docs, tests, and CI config are exempt. There is no override — bump it. Add a matching entry to `claude_resources/neat/CHANGELOG.md`.

Merging to `main` triggers `.github/workflows/release.yml`, which tags `v<VERSION>` (if that tag doesn't already exist) and runs GoReleaser to build/publish `neat` for linux/darwin/windows.
